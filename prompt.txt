## 1. Original Product Vision

DriftGuard is a developer-first SaaS platform that helps applications discover, observe, monitor, understand, and safely adapt to changes in their external dependencies.

The product has three actors:

- **A — External providers:** APIs, third-party SDKs, hosted services, authentication and authorization providers, webhooks, and MCP servers.
- **B — Customer applications:** Software products that consume those external services and want to understand and reduce dependency-related failures.
- **C — DriftGuard:** Our SaaS control plane, developer SDK, dependency collector, monitoring engine, behavioral analysis system, impact analyzer, and constrained recovery engine.

The original customer experience is:

1. A developer creates a DriftGuard project.
2. DriftGuard issues a project-specific ingestion API key.
3. The developer installs the DriftGuard SDK in their application.
4. The developer initializes the SDK using the project configuration and API key.
5. DriftGuard starts collecting permitted, sanitized dependency metadata and runtime observations from supported integrations.
6. The platform builds a versioned inventory of external dependencies and records their observed behavior.
7. DriftGuard compares previous and current observations, provider specifications, and available version metadata.
8. When a meaningful change is detected, DriftGuard identifies the potentially affected application workflows.
9. The platform proposes a minimal compatibility adaptation where appropriate.
10. The candidate repair is validated against deterministic tests before activation.
11. DriftGuard activates a validated adaptation when policy permits, or requires review when evidence is insufficient.
12. The platform retains evidence, version history, audit events, and rollback capability.

The long-term goal is to become an **API Dependency Intelligence and Resilience Platform**, not merely an uptime monitor, API documentation viewer, secret scanner, or AI code-generation tool.

## 3. Add a First-Class Developer SDK

Add a complete SDK specification to the PRD.

For the hackathon, target a lightweight TypeScript SDK for Node.js applications.

### 3.1 Developer experience

Specify a simple integration that resembles:

```typescript
import { DriftGuard } from "@driftguard/sdk";

const driftguard = new DriftGuard({
  apiKey: process.env.DRIFTGUARD_API_KEY!,
  endpoint: process.env.DRIFTGUARD_ENDPOINT,
  environment: process.env.NODE_ENV ?? "development",
});

driftguard.registerDependency({
  name: "users-api",
  type: "rest-api",
  baseUrl: "http://localhost:4001",
});

driftguard.trackRequest({
  dependency: "users-api",
  method: "GET",
  path: "/users/:id",
  statusCode: 200,
  durationMs: 42,
});
```

## 5. Add a Dependency Discovery and Inventory System

The platform must maintain a versioned dependency inventory for each project and environment.

A dependency record should support fields such as:

- Dependency ID and project ID.
- Name and provider, when known.
- Type: REST API, GraphQL API, SDK/package, authentication provider, webhook integration, MCP server, or other supported dependency.
- Base URL or package identifier where appropriate.
- Integration method and discovery source.
- Environment.
- First seen and last seen.
- Observation count.
- Health and confidence status.
- Last observed contract fingerprint.
- Current baseline and latest known version.
- Associated endpoints, tools, or operations where known.
- Related application workflows.
- Collection and redaction policy.

### Discovery sources

Specify and distinguish these sources:

1. **Runtime observations:** Dependencies explicitly registered or observed through supported HTTP clients.
2. **Repository metadata:** Package manifests, lockfiles, API client declarations, and supported configuration files.
3. **Provider contracts:** OpenAPI specifications, GraphQL schemas where accessible, and other supported machine-readable contracts.
4. **Provider change feeds:** Changelogs, version notifications, and webhooks where available.
5. **MCP integrations:** Configured MCP servers, advertised tools, input schemas, and observed tool-call behavior where access is authorized.
6. **Explicit user registration:** Dependencies added manually by the developer.

Discovery must be evidence-based. A package found in a lockfile does not prove that it is active at runtime. An observed request does not prove that all possible endpoints have been discovered.

Track the provenance and confidence of each discovery.

For the hackathon, seed the three existing mock services and implement one real SDK registration/observation path. Keep broad repository scanning and generalized MCP discovery outside mandatory P0 scope.

## 6. Add Change History, Polling, and Monitoring

- Provider webhooks where supported.
- Package-version metadata.
- MCP tool and schema snapshots where supported.

Do not poll arbitrary URLs or endpoints without an explicit configuration and safe access policy.

### Change types

Support a classification model covering:

- Added, removed, renamed, moved, or type-changed fields.
- Nullability and field-presence changes.
- Response and error-envelope changes.
- Status-code and header changes.
- Pagination and ordering changes.
- Authentication or authorization configuration changes when observable.
- Dependency package/version changes.
- MCP tool additions, removals, and schema changes.
- Availability, latency, and rate-limit changes.
- Behavioral or semantic changes where a deterministic probe or workflow invariant provides evidence.

Preserve the existing structural and semantic-drift detection logic.

Each finding must contain the before/after evidence, source, timestamps, classification, evidence strength, affected dependencies and workflows, and a stable deduplication fingerprint.

Distinguish **detected**, **suspected**, and **confirmed** changes. A single anomalous response must not automatically be labelled a provider-wide breaking change.

## 14. Security, Privacy, and Operational Requirements

- Redact sensitive headers and configured body fields locally before transmission.
- Never send raw credentials or arbitrary environment-variable values.
- Use TLS in production.
- Bound queue size, payload size, timeouts, retries, and flush frequency.
- Make network failure non-fatal to the customer's application.
- Provide configurable sampling and collection policies.
- Avoid logging full request/response bodies by default.
- Avoid collecting personal data unless explicitly necessary, authorized, and configured.
- Provide retention and deletion requirements for production.

- Validate all incoming schemas.

- Do not perform unauthorized active probing or replay non-idempotent operations.
- Keep model credentials and provider credentials out of the SDK and telemetry.
- Make clear that development/demo security is not equivalent to production multi-tenant security.
